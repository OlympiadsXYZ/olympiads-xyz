# Задачи: системен дизайн

Как Архивът (PDF-и) се превръща в структурирана, търсима и решаема банка от
задачи, и как тя се свързва с модулите.

## Защо изобщо

Архивът съхранява **файлове**; Наръчникът има нужда от **задачи** — отделни,
адресируеми обекти с условие, фигури, отговор, решение и тема. Само тогава
работят: филтриране по източник/клас/тема/трудност, прогрес по конкретно
състезание, и автоматичното закачане на задачи към модулите.

## Три открития, които определят дизайна

1. **Текстовият слой на PDF-ите е негоден.** `pdftotext` върху НОФ 2019
   връща „Трупче с маса ⟨нищо⟩ се хлъзга…“ — всички числа, символи и формули
   са вградени като обекти и изчезват. Затова транскрипцията е **визуална**:
   страницата се рендира (`pdftoppm -r 160`) и агентът я *чете като
   изображение*. OCR върху текстовия слой не е опция.
2. **Фигурите са вектори, не изображения.** `page.get_images()` връща 0, а
   `get_drawings()` — десетки контури. Затова фигурите се изрязват чрез
   пре-рендиране на правоъгълник (`scripts/pdfcrop.py`, PyMuPDF) при 300 dpi,
   а не чрез изваждане на вградени картинки.
3. **`/problems` стои върху Algolia, който никога не е конфигуриран.**
   Наследено от USACO Guide: `GATSBY_ALGOLIA_APP_ID`/`SEARCH_KEY` липсват, така
   че страницата рендира търсачка без данни. Новият слой **не** зависи от
   Algolia — ползва същия подход като Архива: статични JSON индекси + филтри
   от страна на клиента.

## Модел на данните

Единицата за транскрипция е **изпитната тема** (един PDF = един `paper`), а
единицата за решаване е **задачата** (`problem`). Схема: `problems/schema.json`.

```
content/problems/<subject>/<competition>/<year>/<paper-id>.json
```

```jsonc
{
  "paper": {
    "id": "nof-2019-iii-9",
    "subject": "physics", "competition": "NOF", "year": 2019,
    "round": "III Национален кръг",       // контролиран речник (същият като на Архива)
    "roundType": "theory",                // theory|experiment|practical|observation|data-analysis|test|mixed
    "grade": "9", "lang": "bg",
    "source": { "archiveKey": "Физика/…/NOF3_2019_9problems.pdf", "pages": [1,2] },
    "solutionSource": { "archiveKey": "…9solutions.pdf" },
    "status": "draft",                    // draft -> review -> published (публикува се само след човешки преглед)
    "transcription": { "model": "claude-opus-5", "at": "2026-09-01", "verifiedBy": null }
  },
  "problems": [{
    "id": "nof-2019-iii-9-p1",
    "number": 1, "title": "Хлъзгащо се трупче", "points": 10,
    "statement": "…Markdown + $LaTeX$…",
    "figures": [{ "id": "p1-fig1", "url": "…r2…/problems/nof-2019-iii-9/p1-fig1.png",
                  "width": 1079, "height": 436,
                  "source": { "page": 1, "pdfRect": [51.8,192.6,310.5,297.0], "dpi": 300 } }],
    "parts": [{ "label": "а)", "statement": "…", "points": 5.5,
                "answer": { "kind": "numeric", "value": 10, "unit": "m", "tolerance": 0.05 } }],
    "topics": ["mechanics/energy", "mechanics/friction"],
    "difficulty": "Normal",
    "solution": { "statement": "…", "figures": [] }
  }]
}
```

**Верността е задължителна:** условието се преписва **дословно** — не се
редактира стил, не се „подобрява“ формулировка, не се превежда. Позволени са
само: маркиране на математиката в LaTeX, таблиците като истински Markdown
таблици (никога като снимка) и изрязване на фигурите.

### Типове кръгове

Общото ядро е едно; всеки тип добавя своите полета:

| roundType | добавя |
|---|---|
| `theory` | нищо (само задачи с точки) |
| `experiment` | `apparatus[]`, `measurementTable` (шаблон за данни), `expectedPlots[]` |
| `practical` | `apparatus[]`, `safetyNotes`, стъпки |
| `observation` | `sky` (дата, час, място, условия), `charts[]`, `instrument` |
| `data-analysis` | `datasets[]` (CSV в R2), `plots[]` |
| `test` | `choices[]` + `correct` за всяка задача |
| `mixed` | комбинация — задачите носят собствен `problemType` |

### Отговори

`answer.kind`: `numeric` (стойност + мерна единица + допустимо отклонение),
`expression` (LaTeX + списък еквивалентни форми), `choice`, `text`,
`derivation` (няма автоматична проверка — само решение). Това позволява
проверка на отговор в упражнителния режим там, където е обективно.

## Конвейер (PDF → задачи)

```
1. select    PDF от каталога на Архива (competition/year/round/grade)
2. render    pdftoppm -r 160  →  page-N.png              (визуален вход)
3. segment   агент чете страниците, връща границите: коя задача, кои страници,
             къде са фигурите (bbox в пиксели на прегледа)
4. crop      scripts/pdfcrop.py --box … --dpi 300        (векторите се пре-рендират)
5. transcribe агент пише условието дословно: Markdown + LaTeX + Markdown таблици
6. pair      същото за PDF-а с решенията; решенията се закачат към задачите
7. verify    ВТОРИ агент сравнява JSON срещу оригиналните страници: липсващо
             число, сгрешен индекс, разменени точки, невалиден LaTeX → връща
             дефекти, не оценки
8. upload    фигурите → R2 под problems/<paper-id>/ ; JSON → repo
9. review    човек одобрява преди status: published
```

Стъпка 7 не е формалност: транскрипцията греши тихо (изпуснат долен индекс,
`v_0/2` вместо `v_0`), а тиха грешка в условие е по-лоша от липсваща задача.

## Как се сервира (и защо не статични страници)

Хиляди задачи × статична страница = сигурен OOM на 8 GB build кутията (вече
се случи с 435-те USACO страници). Затова:

- **статична страница на тема** (`/problems/nof/2019/iii-9/`) — рендира всички
  задачи от темата, с котви `#p1`; стотици такива страници, не хиляди;
- **един клиентски индекс на предмет** (`static/problems-data/<subject>.json`)
  — филтри по състезание, година, клас, тема, трудност, тип кръг; същият
  facet подход като в Архива, без Algolia;
- **модулите** сочат към задачи по `id`; съществуващият `*.problems.json`
  механизъм остава — вече с истински линкове към `/problems/…#pN` вместо към
  PDF.

Прогресът ползва вече наличния `ProblemProgress` (Нерешена/Решавам/Решена/
Пропусната) от `UserDataContext` — нищо ново за съхранение.

### Режим „подготовка“

Ученик избира **състезание** (напр. НОФ, областен кръг, 9. клас) или **тема**
(напр. трептения) и получава набор от задачи с прогрес-лента. Наборът е
заявка към клиентския индекс; прогресът се смята от вече съхранените
статуси. Задачите носят `importance` (0–3), за да може „само ключовите“ да е
реален филтър — иначе 3000 задачи са еднакво страшни.

## Ред на изпълнение

1. схема + конвейер + **един** еталонен paper за калибриране (готово: НОФ 2019, III кръг, 9. клас);
2. човешки преглед на еталона → корекции по схемата;
3. чак тогава мащабиране, по семейства състезания, с verifier на всяка тема.

Мащабирането преди калибриране е точно грешката от модулите (виж
`docs/Module-Standard.md`) — не се повтаря.
