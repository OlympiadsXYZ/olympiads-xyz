**Olympiads XYZ: architecture, transcription, and priorities**

Review dated 5 September 2026. Source snapshot: `56b036edaaa2ec44b4ff3ad7c8d06a043388c1eb`.

The project has a sound foundation. Keep the original PDFs, structured problem records, handbook hierarchy, existing progress components, R2 storage, and builds on GitHub Actions. The main change I recommend is to turn transcription into a measurable, resumable data pipeline, with inexpensive models doing routine reading and expensive models handling exceptions. At the same time, connect a useful subset of the growing problem bank to actual preparation paths.

This was a read-only review of the project, with isolated generator experiments outside the repository. I read the design documents, source schema, generator, index/search code, deployment workflow, and Claude workflow scripts; validated every paper against the schema; inspected production index data and live pages; and visually spot-checked the first pages of two physics PDFs. I did not run a Gatsby build, change the live queue, deploy changes, or purchase model calls. No alternative-model accuracy or latency benchmark was run.

**What the evidence says.** The repository contains 379 papers and 1,347 problems. All 379 papers pass the declared JSON schema. Of these papers, 332 have status `review` and 47 have status `draft`; none has status `published`. There are 29 papers without a recorded verifier. All 350 recorded verifications say 4 September, including 184 whose transcription date is later. Those dates are hard-coded in the workflow prompts.

These are provenance and enforcement defects, not evidence that all the text is inaccurate. A missing verifier stamp does not prove no verification happened. Conversely, a populated stamp does not establish independent review of the exact current file.

The live index fetched during the review contained 1,389 total entries, including legacy entries. It matched 1,340 current transcribed IDs; the latest source commit was still building, and recent commits include ID changes. Do not interpret the seven unmatched current IDs as seven proven missing pages. The 47 draft papers and 29 papers without verifier metadata were represented in production. The browser's problem tree displayed 1,347 problems.

**The highest-priority fixes are in the pipeline, before model selection.**

| Priority | Finding and consequence | Recommended change |
|---|---|---|
| P1 | Publication status and verification are ignored by the generator. An isolated fixture with `status: draft` and no verifier produced a page and index entry. | Define what is publishable, enforce it in code and CI, and record approval of a specific content revision. Align the documentation with the intended policy. |
| P1 | Removing a source paper does not remove its generated MDX or index entry. The isolated fixture retained both after regeneration. This undermines quarantine and withdrawal. | Maintain a manifest of generator-owned files and regenerate from the current eligible records. Remove only obsolete generated artifacts; preserve authored solutions. |
| P1 | The answer renderer reads only `parts[].answer`, ignoring `problem.answer`. There are 284 top-level answer objects in the corpus. A fixture's numeric answer was absent from its generated page. | Render supported answer kinds at both levels. This does not mean 284 answers are absent everywhere: some are repeated in solution prose. |
| P1 | `problems-to-site.mjs --check` reports stale MDX but exits 0; it does not compare the complete index. The deployment job builds checked-in artifacts without explicitly running regeneration and the transcription checks. | Make stale outputs and invalid publication evidence fail CI. Validate the source, regenerate, compile, and verify manifest/index consistency before publishing. |
| P2 | Verification metadata is a model-written label with a fixed date, and the workflow's fast path treats an existing promoted file as clean without checking a review record. | Have the runner write actual provider/model identity, timestamps, source hashes, prompt version, content hash, and review results. An existing file alone is not a successful job receipt. |
| P2 | URLs for these problems depend on mutable source/title text. Changing a title or normalizing a grade can change a URL. | Freeze canonical IDs and use ID-based routes or frozen slugs, with redirects for existing URLs. Keep progress IDs stable. |

The spec currently describes human approval before publication, while the working process promotes machine-reviewed material. That may reflect an intentional policy change. I would not make a human read every page by default merely to satisfy an old document. Choose an explicit policy: machine-reviewed archive transcriptions can be published after validated checks and auditing; human-reviewed teaching material remains a separate standard. Show those distinctions honestly. Do not fix this by blindly changing all statuses to `published`.

**The transcription method contains good safeguards, but too much agent work.** The existing workflow explicitly asks both transcription and verification agents to use Opus. Each transcriber downloads PDFs, probes them, renders pages, reads the images, writes JSON, crops and uploads figures, then deletes PDFs and page renders. The verifier downloads and renders again. A separate verification workflow can repair incomplete transcriptions itself, then promote its own repairs. Workflow logic lives under a particular Claude session, while queue/staging state lives in ignored `tmp/`.

Keep visual grounding, verbatim wording, original figures, source-error preservation, and a second check. Change the execution model:

1. **Prepare documents once.** A script downloads the source, records its hash and page count, extracts available text/layout, and renders bounded batches of pages. Cache by document hash and render settings. Reuse the same immutable source images across independent readers. Evict caches by size after review; back up the small durable manifests and review records.
2. **Use a narrow model request.** Give the reader page images or a supported PDF input, a compact schema, and calibrated examples. Request ordered text/formula/table/figure blocks and their source pages. For long documents, split by pages or problem boundaries with overlap and check coverage during assembly.
3. **Automate the mechanical work.** Scripts execute crop rectangles, check bounds and image dimensions, upload immutable assets, validate JSON, compile math/markup, and check URLs. Models may propose figure boxes; they do not need to formulate shell commands or inspect bucket listings for every figure.
4. **Review independently and escalate selectively.** Initially check every paper with a second reader, preferably another model family. The checker sees original pages and the candidate transcription, not the first reader's rationale. Return field-level defects with source locations. Repairs receive checks of the changed regions; a verifier that finishes a missing solution has become its author for that region.
5. **Publish only completed revisions.** Review evidence must identify the source and output hashes. A sole publisher promotes accepted artifacts and runs CI. Failed or ambiguous items remain resumable exceptions.

Use an ordinary script plus a small persistent job store, such as SQLite for one runner. Store states, attempts, provider request IDs, token usage, elapsed time, failure reasons, and content hashes. If multiple hosts later process jobs, use a database designed for shared access. No orchestration platform or GPU cluster is needed for this backlog.

The principle that the printed page is authoritative is correct. The stronger blanket rules are less useful. A text layer that sometimes loses equations can still provide draft text and a cross-check; it should not silently determine the final wording. Likewise, layout detectors can propose figure boundaries even though they cannot certify them. Test extraction routes on real document families and retain visual verification. For a difficult table or illegible passage, an explicitly incomplete page with the original region available is preferable to guessing or blocking all other useful work.

Do not assume that the newest Kimi or GLM flagship is the cheapest appropriate model. Model family, vision capability, reasoning settings, tokenizer, and endpoint all matter. API processing also gives this workload its own metered budget rather than tying it to the interactive Claude workflow and its quota.

**The potential cost reduction is large, but actual task cost must be measured.** As an arithmetic illustration, assume 300 papers, two model calls per paper, and 20,000 billed input plus 6,000 total billed output tokens per call. That is 12 million input and 3.6 million output tokens. It costs approximately $22.50 on Gemini 3.8 Flash at its current standard prices, or $3.60 on GLM-5.3-Flash at list prices. These are hypothetical token bills, not measurements or a completion quote. Different tokenizers, image accounting, long solutions, reasoning, retries, review and repairs can change them substantially.

Gemini Batch halves its listed standard token prices, giving $11.25 for the same illustrative workload. It targets a 24-hour turnaround, so it is the cheaper non-urgent route rather than a promise of the fastest completion. Use bounded online concurrency when turnaround matters. [Batch documentation](https://ai.google.dev/gemini-api/docs/batch-api)

**A small comparison should decide the model.** Start with 24 representative papers, not the entire remainder: clean digital exports, embedded-equation PDFs, old/skewed scans, dense tables, figures and multi-page problems, mixed grades, and astronomy practical/observational material. Include known difficult cases and a random selection from the unfinished backlog. Keep some papers held out from prompt tuning.

Compare GLM-5.3-Flash and Gemini 3.8 Flash on identical inputs; add GLM-OCR as an extraction route and Kimi only if convenient. Compare their final reviewed output with the current Opus workflow, using human-adjudicated PDF truth rather than assuming the old Opus JSON is a gold standard.

Measure omitted problems/clauses, incorrect signs/digits/subscripts/units, formula equivalence, table cells, figure coverage/cropping, statement/solution pairing, and preservation of printed mistakes. Also record dollars and elapsed time **per accepted paper**, retries, escalation rate, and reviewer minutes. Separate statement errors from solution errors and transcription defects from source defects.

Use the pilot to choose a route and expose systematic failures. Twenty-four clean papers cannot establish a very low residual error rate. Continue audits during staged rollout, and only reduce second-pass coverage when measured results justify doing so. Model agreement or a self-reported confidence number is not certification. Reserve Opus/Fable-level work for unresolved visual ambiguity, difficult repairs, and pedagogical judgment.

**The larger product needs attention alongside the corpus.** None of the current transcribed IDs matched in the fetched live index had a handbook module association. There are 1,019 distinct topic strings for 1,347 source problems, including parallel names such as `mechanics/kinematics`, `physics/mechanics/kinematics`, and `kinematics/relative-motion`. The live search UI offers useful filters, but its search box matches only problem title and source text. It does not search statements. | Decision | Recommendation |
|---|---|
| Core framework | Keep Gatsby for this iteration. Benchmark build time, artifact size, and page performance as the corpus grows; migrate only against a demonstrated bottleneck. |
| Hosting | Keep builds off the Mac. Keep the existing GitHub-to-deploy-branch approach while it works; add source/artifact consistency gates. |
| Canonical data | Treat structured source records as canonical and MDX/search/tree data as derived. The page editor currently targets generated MDX; redirect edits to canonical records or an intentional review workflow. |
| Document versus paper | Allow a paper to reference multiple documents and a document to contain multiple grades/papers. The schema already distinguishes problem and solution sources; extend source spans rather than assuming every PDF is one assessment. |
| Archive linking | Retain catalogue identifiers and source hashes alongside readable keys. Reuse known metadata; visually adjudicate conflicts instead of re-inferring all metadata every time. |
| Problem provenance | Add page/region references for statements and solutions, not just paper-level page arrays and figure rectangles. Let Compare jump directly to the relevant page. |
| Topic taxonomy | Maintain a small controlled vocabulary with aliases and Bulgarian labels. Models propose tags from that list. Topic classification and exact transcription should be separate revisions. |
| Difficulty and importance | Mark estimates as estimates until calibrated. Do not turn an unreviewed model guess into an authoritative preparation priority. |
| Answers and grading | Preserve the official answer first. Keep generated answer summaries and grading rules distinct. A prompt asking for a “sensible tolerance” is not a grading specification; defer automated checking until equivalence, units and tolerances are designed. |
| Student discovery | Add explicit subject/competition/year/grade facets and statement search; preserve filters in URLs. Keep compact metadata indexes and fetch bodies on demand. A vector database is unnecessary for this requirement. |
| Completeness | Distinguish “source lacks a solution,” “solution not transcribed,” and “solution reviewed.” Do not equate an internal page route with availability of an official solution. |
| Learning experience | Link selected problems into the Kinematics exemplar with prerequisites, graduated practice and hidden hints/solutions. Keep exam-year browsing as another entry point. |
| Issue reports | Keep Compare and reporting. GitHub issues are adequate for early technical testers; consider an easier student-facing report form if GitHub login becomes a participation barrier. |
| Work durability | Put pipeline code, prompt versions and evaluation fixtures under version control. Keep secrets out. Back up resumable job state outside a single Mac/session. Ignored `tmp/` surviving a reboot is not itself a backup. |
| Progress measures | Track accepted problems, critical defects, correction time, cost per accepted paper, and student practice completion. Raw paper counts are useful inventory, but incomplete as the project's success measure. |

There are positive counterexamples to a blanket criticism of Fable's work. The NOF 2019 exemplar statement I inspected preserves the easily lost fractions, negative work value and other quantities. The live PSF 2006 problem I inspected rendered equations correctly despite older warning logs; I am not reporting those old warnings as a present production defect. The live NAO 2015 junior problem 3 visibly explains that the official source lacks its solution. Preserve this care and make it systematic.

**Suggested next sequence.** Let in-flight work finish safely, but hold additional large Opus launches while the pilot is prepared. First repair the publication/withdrawal/answer/check behavior and establish durable provenance. Then run the small paid model comparison under a chosen spending cap and migrate one measured batch. In parallel with corpus expansion as project work, connect roughly 20–30 reviewed problems to one coherent Kinematics preparation path and test it with a few students or teachers. Use those observations to choose the next corpus slice and handbook module.

The intended asset is a trustworthy preparation system: find the right material, learn the method, attempt a suitable problem, get useful feedback, and know what to do next. Cheap, accurate transcription is an enabling component of that system. It should free attention for those learning decisions.
